# Cloud Mail 安全更新与回滚

本文针对 `VanteeCN/cloud-mail` 的现有部署。命令在 Windows PowerShell 中执行；每一步成功后再进入下一步。日常更新顺序是：**备份 → 更新分支合并 → 本地验证 → 检查并迁移数据库 → 推送 main → 验收**。

## 1. 当前部署方式

| 项目 | 当前值 |
| --- | --- |
| 自己的仓库 origin | `git@github.com:VanteeCN/cloud-mail.git` |
| 源仓库 upstream | `https://github.com/maillab/cloud-mail.git` |
| Cloudflare Worker | `cloud-mail` |
| 生产分支 | `main` |
| Cloudflare 构建根目录 | `/mail-worker` |
| Cloudflare 构建命令 | 留空，由 Wrangler 的 `[build]` 构建前端 |
| Cloudflare 部署命令 | `npx wrangler deploy` |
| D1 绑定 | `db` → 现有数据库 `mail` |
| KV 绑定 | `kv` → 现有命名空间 `mail` |
| 其余绑定 | `ai`、`assets` |

本 fork 使用 **Cloudflare Workers Builds** 监听 GitHub。推送 `main` 就会自动部署，不需要再手动运行一次 Wrangler。GitHub Actions 在本 fork 中未启用，保持这个状态，避免两条流水线同时发布。

控制台目前也启用了非生产分支构建。更新分支先只留在本地；不要把连接生产 D1/KV 的预览当成隔离测试环境。如需云端预发布，先准备独立数据库、KV 和配置。

本仓库的定制配置在 `mail-worker/wrangler.toml`：明确声明现有 D1/KV 的 ID，并设置 `keep_vars = true`。`admin`、`domain`、`jwt_secret` 仍由 Cloudflare 控制台管理。**`keep_vars` 只负责保留变量，不能代替数据库/KV 绑定声明。** 不要把 JWT、API Token、密码或数据库导出文件提交到公开仓库。

## 2. 更新前保存回退点

```powershell
Set-Location E:\code\cloud-mail
git status --short --branch
git switch main
git pull --ff-only origin main
$updateStamp = Get-Date -Format 'yyyyMMdd-HHmmss'
git tag "backup/pre-update-$updateStamp"
git push origin "refs/tags/backup/pre-update-$updateStamp"
git switch -c "codex/update-$updateStamp"
```

如果 `git status` 显示改动，先检查并单独提交自己的改动，再开始更新。`git pull --ff-only` 失败时先处理分支差异，不要执行强制覆盖或 `reset --hard`。

然后在 Cloudflare 做两件事：

1. 打开 **Workers 和 Pages → cloud-mail → 部署**，记录当前生产版本完整 ID（可以用复制按钮），确认它的绑定和域名。
2. 打开 **存储和数据库 → D1 → mail → 按时间顺序查看（Time Travel）→ 获取当前书签 ID**，把书签和时间保存在本机的 `.update-backups/<日期>/`。本账户在本次更新时显示的恢复窗口是 **7 天**，以后以页面实际显示为准；书签不会延长这个窗口。

如需长期备份，可额外导出 D1。下面命令需要本机 Wrangler 已登录；未登录时先执行 `pnpm --dir mail-worker exec wrangler login` 并在浏览器完成本人授权。不要在聊天或文档中粘贴 Token。

```powershell
New-Item -ItemType Directory -Path .update-backups -Force
pnpm --dir mail-worker exec wrangler d1 export mail --remote --output "../.update-backups/mail-$updateStamp.sql"
```

确认命令成功且导出文件存在，并另存一份到受控备份位置。D1 导出不包含 KV/R2/S3 中的附件和缓存；更新时继续复用原存储资源，不清空或替换它们。

## 3. 获取上游，保留自己的改动

第一次配置 upstream 时执行一次（已存在就跳过）：

```powershell
git remote add upstream https://github.com/maillab/cloud-mail.git
```

每次更新：

```powershell
git fetch upstream --tags
git log --left-right --oneline HEAD...upstream/main
git diff --stat HEAD...upstream/main
git diff HEAD...upstream/main -- mail-worker/src/init/init.js mail-worker/wrangler.toml mail-worker/package.json mail-vue/package.json .github/workflows
git log upstream/main..HEAD --oneline
git merge --no-edit upstream/main
```

合并是在本地更新分支进行，尚未影响线上。若要固定某个发布版本，可把上述目标 `upstream/main` 换成已核实的 tag，例如 `v3.4.0`。

发生冲突时逐项编辑文件、删除冲突标记，保留自己的功能和部署资源 ID，然后 `git add <已解决文件>`、`git commit`。不要对整个仓库使用“全部采用上游”。拿不准时 `git merge --abort` 返回合并前状态，生产仍是旧版。

每次必须检查：`wrangler.toml` 的 Worker 名、D1/KV ID、`keep_vars = true`、静态资源目录以及 Cron。不要用 `wrangler-action.toml` 的占位符配置替代当前配置，也不要误改为新建数据库。

## 4. 本地构建和部署预检

本次验证环境为 Node.js `24.14.1`、pnpm `10.33.0`。以后先检查上游依赖的运行版本要求。安装依赖使用已有 lockfile，不要在更新应用时顺手升级全部依赖。

```powershell
node --version
pnpm --version
pnpm --dir mail-worker install --frozen-lockfile
pnpm --dir mail-vue install --frozen-lockfile
pnpm --dir mail-worker exec wrangler deploy --dry-run --outdir .wrangler/update-check
git diff --check
git status --short
```

`--dry-run` 会调用 `[build]` 构建前端并打包 Worker，成功后输出绑定表，不会发布。确认绑定包含 `db (mail)`、正确的 `kv` ID、`ai` 和 `assets`。构建失败或 lockfile 不匹配时停在更新分支处理，不能继续推送生产。

上游自带的 `mail-worker/test/index.spec.js` 仍是 “Hello World” 模板，且测试配置引用了不存在的 `wrangler.jsonc`，不能把它作为本项目已完成自动回归测试的依据。需要运行时测试时使用本地模拟 D1/KV、测试域名和测试密钥；不要用 `wrangler dev --remote` 测试生产数据。

## 5. 数据库迁移：先查结构，再切换代码

对照本次上游差异检查 `mail-worker/src/init/init.js` 和 `src/entity/`。每个版本的 SQL 可能不同，下面 SQL **只适用于升级到 v3.4.0**，以后不要不加检查重复执行。

在 D1 的 `mail` 控制台先执行只读查询：

```sql
SELECT name, type, dflt_value
FROM pragma_table_info('email')
WHERE name = 'sender_email';
```

若返回 0 行，且已记录 Time Travel 书签，执行仓库中的 `doc/migrations/v3.4.0.sql`：

```sql
ALTER TABLE email ADD COLUMN sender_email TEXT NOT NULL DEFAULT '';
```

再次运行上面的查询，确认新增列为 `TEXT`，默认值为空字符串。若列已存在则跳过，SQLite 不支持这里的 `ADD COLUMN IF NOT EXISTS`。本次旧版数据库已有 v3.3.0 的设置字段和索引，因此无需重复旧迁移。

本次是兼容旧代码的新增字段，可以先迁移再发布，避免新版收信时写入缺失的列。**以后遇到删列、重命名或修改数据含义的迁移，要单独安排维护窗口和恢复方案，不能照搬这个顺序。**

不要为了这次单个新增字段反复访问 `/api/init/<jwt_secret>`：它会运行所有历史初始化逻辑，并把密钥带入 URL。一般升级应逐项审查并执行实际缺失的迁移；也不要在公开截图中展示密钥。

## 6. 发布到 Cloudflare

把本地配置、文档等修改提交到更新分支。先用 `git diff` 检查提交内容；本机备份目录已经加入 `.gitignore`。

```powershell
git diff
git add mail-worker/wrangler.toml .gitignore README.md doc
git commit -m "chore: preserve deployment settings and document safe upgrades"
git switch main
git pull --ff-only origin main
git merge --ff-only "codex/update-$updateStamp"
git push origin main
```

分支名使用第 2 步实际生成的名字；若本次没有配置/文档等待提交的修改，就跳过 `git add` 和 `git commit`。如果期间别人更新了 main，最后的快进合并可能失败：返回更新分支合并最新 `origin/main` 并重新验证，不要 force push。

推送后打开 **cloud-mail → 部署**，等待对应提交的构建完成。确认：构建状态成功、提交 hash 正确、新版本获得 100% 流量。若构建失败，线上通常仍运行旧版，先看失败日志，修复后重新构建。

## 7. 发布后验收

- 打开自己的站点，刷新页面，检查标题、登录状态和原有设置。
- 检查收件箱、全部邮件、已有邮件正文、搜索和附件；确认没有“请更新数据库”或绑定缺失提示。
- Cloudflare 概述中的 D1/KV 仍绑定到原资源；检查自定义域名、邮件路由和 Cron。
- 在可用的测试邮箱间人工验证一次收发。发送会产生真实邮件，不要用批量发信做升级验证。
- 查看 Worker 错误日志，确认没有新增数据库字段错误、500 或附件读取错误。
- 必要时比较升级前后的用户、邮箱和邮件数量。系统仍在收信，数量正常增加是允许的。

公开配置接口可用下面命令检查；不能只看 HTTP 200，还要检查 JSON 的业务状态：

```powershell
$siteConfig = Invoke-RestMethod 'https://giao.giaoai.com/api/setting/websiteConfig'
if ($siteConfig.code -ne 200) { throw '网站配置接口检查失败' }
```

保存本次生产版本 ID、Git 提交、迁移 SQL、D1 书签和验证结果，作为下次更新的起点。

## 8. 回滚

### 先回滚 Worker，保留现有数据

在 **cloud-mail → 部署** 找到更新前记录的完整版本 ID，选择回滚并确认 100% 流量。选包含原 D1/KV 绑定的生产版本，不要只凭旧代码提交选择一个曾经缺少绑定的版本。随后重新检查站点、邮件和绑定。

v3.4.0 新增的 `sender_email` 列可以保留，旧版能够继续运行，无需为了代码回滚去删列或恢复整个数据库。

### 同步修复 Git，避免下次构建再次发布坏版本

Cloudflare 的版本回滚不会自动改变 GitHub。不要使用 `git reset --hard` 加 `push --force`。

若需要完整退回某个已验证的代码树，可以在一个修复分支执行以下命令，手动检查差异后合并并正常推送 main（把 `<备份标签>` 替换为实际标签）：

```powershell
git switch -c codex/rollback-fix main
git restore --source <备份标签> --staged --worktree -- .
git diff --cached --stat
```

**备份标签中的旧 `wrangler.toml` 可能还没有 D1/KV 声明。提交前必须补回当前正确的绑定和 `keep_vars = true`**，并保留所需更新文档。重新运行构建预检，确认后提交、合并 main、普通推送。对于单个已知问题也可以使用 `git revert <有问题的提交>`；合并提交需要先确认主线父提交，再考虑 `git revert -m 1`。

### 只有数据损坏时才恢复 D1

如果迁移真的损坏了数据，在 D1 → Time Travel 使用保存的书签恢复。恢复会覆盖书签之后的新邮件、用户等数据库变化，因此先暂停相关写入、导出当前状态，并核对这段时间的数据；不要把数据库恢复当作普通代码回滚步骤。恢复操作本身不回滚 KV/R2/S3 文件，也不回滚 Worker。
